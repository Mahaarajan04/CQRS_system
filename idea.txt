Here's what was on the roadmap after Saga, ranked by impact for your DB project:

1. Read-your-writes cache (your idea — high value)
Redis cache layer the write API populates on each successful command. Read API checks Redis first before hitting PostgreSQL. Closes the eventual-consistency window to ~0ms for the order you just placed. Demonstrates a real CQRS problem + solution.

2. Outbox pattern (hardens the write path)
Right now events.py does insert_mongo → xadd_redis. If the process crashes between them, the event is in Mongo but never published. Outbox fixes this: write event + outbox row in one Mongo transaction, separate poller reads outbox → publishes to Redis → marks published. Guarantees at-least-once delivery under crashes. DB-course-relevant because it's a classic "2 databases, no distributed transaction" problem.

3. Snapshotting (scale + replay benchmarks)
When an aggregate has 1000+ events, replaying from v1 is slow. Snapshot every N events: store current state in a snapshots collection. Replay starts from latest snapshot + remaining events. Bench the replay time before/after → concrete numbers for your report.

4. Saga timeout / recovery cron
Currently if the saga worker crashes mid-flight, the saga is stuck. Add a periodic job that finds sagas in non-terminal states older than N seconds and resumes them. Shows off the crash-recovery design you already built.

5. Frontend dashboard (demo polish, not DB-relevant)
Minimal React/HTML page showing live orders + saga states + inventory. Good for presentation but doesn't deepen the DB content.

My suggestion order: cache → outbox → snapshotting. Cache because it's your idea and high-visibility. Outbox because it plugs a real gap. Snapshotting because it gives you measurable benchmarks for the report.
